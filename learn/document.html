Document databases

Also called “NoSQL” or non-relational. Each record is a self-contained document that can have its own shape, a bit like a filled-in form. Great when no two records look alike.

The example data is made up: a small neighbourhood bakery. Use the arrow keys or the dots to step through.

The short version

✓ Great for

  • Product catalogs where every item has different specs
  • User profiles and settings that keep evolving
  • Content, form submissions, event logs
  • Apps that read one whole record at a time, at large scale

✗ Watch out for

  • Questions across many documents (totals, reports) are harder
  • Copied details drift out of date (a name changed in one place only)
  • Fewer built-in rules, so the app has to enforce them
  • Easy to make a mess without a plan for how data will be read

When every record has a different shape, or the shape keeps changing, and you mostly read one record at a time, use documents.

Common tools

MongoDB, Amazon DynamoDB, Google Firestore, Couchbase, JSON columns in Postgres

From my work

I’ve built data lakes where semi-structured files sit in cloud storage and get queried as-is, alongside a SQL warehouse. Each shape does the job it’s good at.
